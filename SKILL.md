# Лабораторные работы по ИТ-дисциплинам — универсальный workflow

Скилл для выполнения лабораторных работ по программированию и ИТ-дисциплинам
в любом вузе, для любого студента и любого принимающего. Не привязан ни к
вузу, ни к дисциплине, ни к исполнителю: все данные — вуз, студент,
преподаватель, вариант — берутся из опроса пользователя и `_context.json`,
никогда из предположений.

## Обязательное доказательство выполнения и приоритет инструментов

Для каждой ЛР с исполнимым исходным кодом раздел «Результат выполнения» обязан содержать PNG фактического запуска. Текстовый `code` с ожидаемым выводом не заменяет доказательство и может быть только пояснением рядом с изображением. CLI снимается из настоящего окна терминала, веб-работа — из реальной страницы, нативный интерфейс — из работающего окна.

При активном workflow этого skill сначала используй bundled-инструменты из `scripts/`: `run_cli_shot.ps1` для CLI-доказательств в отдельном окне, `shot.ps1` для нативных окон терминала/GUI, `cdp.js` для браузерных страниц, `lab_runner.py` для сборки и проверок, `docx_text.py` для извлечения текста из DOCX. Глобальный skill `screenshot` — fallback, когда требуется OCR либо работа с активным пользовательским окном; он не заменяет `run_cli_shot.ps1` или `shot.ps1` для отчётного доказательства.

## Главные принципы

1. **Одна лабораторная работа за раз.** Никогда не начинай следующую, пока
   текущая не согласована с пользователем. Цикл: выполнил → отчитался (что
   сделано, где лежит, что проверить) → пользователь проверил → его замечания →
   правки → только потом следующая.
2. **Никаких выдуманных данных.** Вуз, ФИО, группа, преподаватель, вариант,
   тема — только из `_context.json` или из прямого ответа пользователя.
   Данных нет — спроси.
3. **Переносимость.** Все пути — относительные от корня проекта. Ничего не
   хардкодь в скриптах: каждый проект — свой контекст.
4. **Продолжение без потери контекста.** Постоянные данные титульника живут
   в `_context.json`, а ход конкретных работ — в `_lab_state.json`. При
   возобновлении сначала прочитай оба файла и не переспрашивай уже
   подтверждённое.

## Шаг 0 — сбор контекста

Прочитай `_context.json` в корне проекта (рядом с `_tools/`). На старте
проекта этого файла не существует — его создаёшь ты сам по итогам опроса.
Возможные состояния проекта:

- **голая папка** — опроси с нуля и создай всю структуру;
- **неорганизованная папка** (методички и файлы вперемешку) — опроси,
  разложи по структуре из следующего раздела;
- **организованный проект** (готовые лабораторные работы) — опроси недостающее,
  сверь структуру проекта со стандартной.

Если в проекте есть иные файлы с уже утверждёнными ранее данными (план
работ, README, `_context.json` смежного проекта) — используй их как источник:
не переспрашивай того, что там уже подтверждено, спрашивай только то,
чего не хватает.

Если `_context.json` уже есть (создан при прошлых работах) — не опрашивай
с нуля: покажи пользователю текущие данные и попроси подтвердить, что они
актуальны. Если файла нет или какие-то поля пусты — спроси у пользователя
ВСЁ недостающее одним списком:

- вуз/институт/кафедра и **образец титульного листа** (файл, скан или текст);
- ФИО и группа студента;
- ФИО, должность и учёное звание принимающего преподавателя;
- город и учебный год, дисциплина;
- номер варианта выполнения;
- тема лабораторной работы и методичка (файл или ссылка);
- особые требования к отчёту и порядку сдачи;
- используется ли git; если репозитория нет — нужно ли инициализировать.

Шаблон `_context.json`:

```json
{
  "university": ["строки шапки титульника", "по порядку"],
  "discipline": "",
  "student": "", "group": "",
  "teacher": "", "teacher_title": "",
  "city": "", "year": "",
  "variant": "",
  "git": true
}
```

`university` — список строк верхней части титульного листа в порядке
следования; остальные титульные поля идут как есть; `variant` нужен для
выбора задания из методички; `git` — использовать ли git в этом проекте.
Заполнив — сохрани файл и продолжай.

## Состояние работ — `_lab_state.json`

`_context.json` содержит постоянные данные студента и титульного листа. Для
переноса работы между сессиями и компьютерами веди рядом с ним
`_lab_state.json`: он хранит изменяемое состояние лабораторных и
подтверждённые проектные решения, но не дублирует персональные данные или
текст заданий из методичек.

Методичка, указанная в `methodical_guide`, — первичный источник официального
номера, темы, задания и требований. Имя каталога — только рабочий путь. Если
данные методички противоречат `report_number` или `theme` в состоянии,
покажи противоречие пользователю и запроси уточнение, а не выбирай молча.

```json
{
  "version": 2,
  "commit_on_completion": false,
  "project_notes": ["Подтверждённое решение проекта, которого нет в методичке"],
  "labs": {
    "1": {
      "status": "in_progress",
      "directory": "ЛР1",
      "methodical_guide": "ЛР1/методичка.pdf",
      "report_number": 9,
      "theme": "Тема лабораторной работы",
      "variant": "9",
      "shared_resources": ["_libs/библиотека.js"],
      "notes": ["Подтверждённое решение именно этой ЛР"],
      "next_step": "Собрать и проверить отчёт",
      "commands": {"build_report": "py _tools/make_docx.py ...", "verify": "py _tools/verify.py"},
      "command_templates": {"functional_check": "node cdp.js run --url file:///... --eval ..."},
      "tooling": {"report_inspector": "bundled:inspect_docx"},
      "verification": {
        "status": "passed",
        "checked_at": "2026-10-01T12:34:56Z",
        "checks": ["content_references", "artifacts", "report_docx", "report_pdf", "text_docx"],
        "warnings": []
      },
      "artifacts": ["ЛР1/Отчет_ЛР1.docx"]
    }
  }
}
```

`directory` — необязательный относительный рабочий каталог; если его нет,
используется `ЛР<ключ labs>`. `report_number` — необязательный официальный
номер для титульника; если его нет, используется ключ записи для обратной
совместимости. `directory` и `methodical_guide` не могут быть абсолютными
путями. `shared_resources` — относительные ссылки на общие ресурсы, которые
не надо копировать в каждую ЛР. `artifacts` может перечислять как готовые
файлы, так и каталоги результатов (например, `screenshots/`). `project_notes` и
`notes` хранят только утверждённые решения, отсутствующие в методичке.
`commands` содержит только фактически выполненные и воспроизводимые команды: не
сохраняй в нём абсолютные пути к профилю пользователя или глобальному skill.
Для схем, сокращений и команд с подстановками используй отдельный необязательный
объект `command_templates`. `tooling` — необязательный объект с логическими
ссылками на общие скрипты вида `bundled:inspect_docx`, `bundled:pdf_text`,
`bundled:docx2pdf`, `bundled:docx_text`, `bundled:cdp`, `bundled:shot` или
`bundled:lab_runner`; runner разрешает их относительно собственного каталога. `verification` — необязательная сводка
последней проверки (`status`, UTC-время `checked_at`, списки `checks` и
`warnings`); она не заменяет повторный quality gate. Создавай записи только для
известных лабораторных. Допустимые `status`:
`not_started`, `in_progress`, `ready_for_review`, `completed`.

Минимальный жизненный цикл записи: перед началом практической части поставь
`in_progress`, укажи ближайший незавершённый шаг в `next_step` и добавляй
созданные артефакты по мере появления. После каждого изменения состояния выполни
`validate-state` (см. ниже). Только после успешного quality gate, который создаёт
факт-подтверждение `ЛРN/quality_gate.json`, поставь `ready_for_review`; после
явного подтверждения пользователя — `completed` и обнови `next_step`. Добавляй
`quality_gate.json` в `artifacts`, когда нужен переносимый журнал готовности.
После каждого существенного этапа сохраняй проверенные команды, актуальные
`next_step` и список готовых артефактов. При старте следующей сессии покажи
краткое резюме записи и уточни только недостающие либо устаревшие данные.

`commit_on_completion` по умолчанию `false`. Он разрешает автоматический
коммит только если пользователь заранее включил его сам; иначе всегда получи
прямое согласие перед коммитом.


## Новый проект: подготовка инструментов

Набор инструментов скилла — в `<папка скилла>\scripts\`:

| Файл | Назначение | Где живёт |
|---|---|---|
| `make_docx.py` | сборщик .docx (отчёт, конспект) | копируется в `_tools/` проекта |
| `docx2pdf.ps1` | docx → pdf (Word COM) | из папки скилла |
| `cdp.js` | CDP-управление Edge: снимки страниц, JS, диалоги, popup; `reset` очищает зависший профиль | из папки скилла |
| `shot.ps1` | снимок окна/региона ОС | рядом с `cdp.js` (харнес зовёт сам) |
| `run_cli_shot.ps1` | запуск CLI в отдельной UTF-8 консоли и снимок по уникальному заголовку | рядом с `shot.ps1` |
| `pdf_text.py` | извлечение текста из PDF (pymupdf) | из папки скилла |
| `docx_text.py` | извлечение текста из DOCX для содержательной проверки | из папки скилла |
| `inspect_docx.py` | структурная проверка абзацев, таблиц, листингов и рисунков DOCX | из папки скилла |
| `lab_runner.py` | ASCII-safe сборка, конвертация и проверка по `_lab_state.json` | из папки скилла |

Дублируется в `_tools/` только `make_docx.py` — он единственный, кто
адаптируется под проект/вуз. Остальные запускай напрямую из папки скилла,
копии не нужны (и не разойдутся при обновлении скилла). Если у проекта уже
свои харнесы в `_tools/` — сначала прочитай их докстринги и используй их.

Если в проекте нет сборщика отчётов `_tools/make_docx.py`:

1. Скопируй: `Copy-Item <папка скилла>\scripts\make_docx.py _tools\`
2. Сверь титульный лист с образцом вуза пользователя: скрипт строит типовой
   титульник вузов РФ из данных контекста (шапка из `university`, «Выполнил»/
   «Принял», город и год внизу).
3. Создай `_context.json` (Шаг 0) и проверь генерацию на пробном отчёте.

Титульник вуза отличается от типового только формулировками — добейся нужного
вида опциональными полями контекста (`performed_prefix`, `accepted_prefix`,
`report_label`, `discipline_label`, `theme_label`; полный список — в докстринге
`_tools/make_docx.py`), код не правь. Структура образца принципиально другая —
адаптируй `title_page()` в скрипте под образец; вуз-специфичная адаптация живёт
только в `_tools/` проекта — в скилл её не копируй (иначе в универсальный скилл
попадёт шапка конкретного вуза).

Если в проекте уже есть свой сборщик отчётов или шаблон — изучи его и сравни
с bundled-версией этого скилла (возможности, формат содержимого, кодировка,
рисунки и листинги). Если имеющаяся реализация хуже — предложи пользователю
доработать её или заменить; решение за пользователем, молча не заменяй.

## Структура проекта

```
ЛРN/                  — лабораторные работы по одной в папке (ЛР1, ЛР2, ..., ЛРN)
  код работы          — исходники, страницы, данные лабораторной
  screenshots/        — PNG-скриншоты для отчёта
  img/, downloads/    — по необходимости работы
  content.json        — содержимое отчёта
  content_text.json   — содержимое text.docx
  Отчет_ЛРN.docx      — отчёт
  Отчет_ЛРN.pdf       — тот же отчёт в PDF
  text.docx           — конспект для защиты (имя неброское — так задумано)
_libs/                — необязательно: локальные общие зависимости нескольких ЛР
_tools/make_docx.py   — сборщик .docx
_context.json         — постоянные данные контекста (титульник, вариант, git)
_lab_state.json       — ход лабораторных, команды и готовые артефакты
```

Имена `text.docx` и `Отчет_ЛРN.*` — фиксированные соглашения, не переименовывать
и не «улучшать». Если попались старые/иные имена отчётов — приведи к стандарту
при очередной работе с этой лабораторной.

## Выполнение лабораторной работы — workflow

1. Уточни номер лабораторной работы. Задание ищи в методичке пользователя:
   PDF читай сначала read-инструментом, а если он PDF не берёт — извлеки
   текст: `py C:\tools\lab-skill\scripts\pdf_text.py guide.pdf 1-5`.
   В примере используются только ASCII-пути; при кириллическом пути запускай
   runner из корня проекта вместо передачи пути через shell.
   Диапазон 1-based включительный; выход за последнюю страницу ограничивается с
   предупреждением, а некорректный диапазон завершает команду понятной ошибкой.
   (нужен pymupdf: `pip install pymupdf`). Путь спроси, если не очевиден.
   Если методичка относится только к этой ЛР и находится в корне либо в
   неорганизованной папке проекта, **перемести, а не копируй** её в `ЛРN/`
   до начала практической части и укажи новый относительный путь в
   `_lab_state.json`. Не оставляй дубликат в корне. Исключение — явно
   общая методичка для нескольких ЛР: оставь один экземпляр в общем месте и
   зафиксируй его как общий ресурс.
2. Выполни всю работу в папке `ЛРN/`.
3. Скриншоты для отчёта обязательны для исполнимой работы: помести PNG фактического результата в `ЛРN/screenshots/`, добавь его в `artifacts` и вставь элементом `img` после заголовка «Результат выполнения». Для CLI предпочитай `lab_runner.py --action capture-cli`, предварительно указав воспроизводимую команду в `labs.N.commands.cli_evidence`; затем выполни `--action check-screenshot`. Он технически проверяет PNG без открытия окон и не забирает фокус. Затем действуй по разделу «Скриншоты для отчёта» (CDP-харнес:
   статика, интерактив, диалоги, popup), PNG в `ЛРN/screenshots/`, имя —
   по смыслу страницы/состояния (`index.png`, `dialog_prompt.png`).
   «Чистые» ОС-скриншоты (не связаны со страницей) — через скилл screenshot.
4. Собери отчёт (раздел «Отчёт») → `ЛРN/Отчет_ЛРN.docx`.
5. Собери `ЛРN/text.docx` (раздел «Конспект для защиты»); предпочтительно
   runner-действием `build-text`.
6. Конвертируй отчёт в PDF (раздел «PDF») → `ЛРN/Отчет_ЛРN.pdf`;
   предпочтительно runner-действием `build-pdf`.
7. Выполни `inspect-documents`, затем quality gate из раздела «Проверка
   отчёта», сохрани команды и подтверждённые файлы в `_lab_state.json`, затем
   поставь `ready_for_review`. `prepare-report` может выполнить полный цикл
   сборки, инспекции и quality gate одним действием.
8. Отчитайся пользователю: что сделано, где лежит, что проверить. Жди
   проверки, вноси правки до согласования; после согласования поставь
   `completed`.
9. Если в проекте используется git (Шаг 0) — предложи коммит в стиле
   существующих в репозитории (посмотри `git log`), например
   `LR3: краткая суть работы`. Выполняй его только по прямому запросу
   пользователя либо при `commit_on_completion: true`.

### Временные файлы

Перед финальным `quality-gate` удали временные артефакты, созданные для
автоматизации или промежуточной обработки: демонстрационные сценарии, распакованные
каталоги DOCX, тестовые снимки, логи и другие файлы, не нужные для воспроизведения
либо сдачи. Не удаляй исходный код, методичку, фактические PNG-доказательства,
отчётные материалы и иные файлы из `artifacts`. `__pycache__/` и аналогичные
генерируемые каталоги не добавляй в `artifacts` и исключай из коммита, если они не
уже игнорируются правилами проекта.

## Отчёт (make_docx.py)

Для путей или темы с не-ASCII символами предпочитай runner-действие
`build-report`, которое читает их из состояния. Ручной запуск допустим только
с уже ASCII-safe аргументами:

```text
py _tools\make_docx.py --out lab\report.docx --num 1 --theme "Sample theme" --content lab\content.json --context _context.json
```

Содержимое отчёта — `ЛРN/content.json`, список элементов:

| Элемент | Что делает |
|---|---|
| `{"h": "Заголовок"}` | полужирный TNR 14 pt |
| `{"p": "текст"}` | абзац TNR 16 pt |
| `{"code": "..."}` / `{"codefile": "путь"}` | листинг Courier New 12 pt |
| `{"img": "screenshots/x.png", "caption": "Подпись"}` | рисунок по центру + подпись |
| `{"table": {"rows": [[...]], "widths": [dxa], "header": true}}` | таблица с границами; шапка жирная с заливкой |
| `{"pb": true}` | разрыв страницы |

**Много-заданиевые лабораторные** (более одного задания — типовой случай
для методичек на 15–20 заданий): каждое задание — отдельный раздел того же
content.json, порядок секций = порядок заданий в методичке:

```json
{"h": "Задание N. <название из методички>"},
{"p": "Формулировка. <текст формулировки из методички>"},
{"p": "Текст программы (ExN.html):"},
{"codefile": "ExN.html"},
{"img": "screenshots/exN.png", "caption": "Рисунок N — результат работы страницы ExN.html"},
{"pb": true}
```

Подписи рисунков — сквозной нумерацией «Рисунок N» по порядку в отчёте,
`{"pb"}` между заданиями.

Для `table`: `rows` — непустой список строк одинаковой длины; `widths` —
необязательные ширины столбцов в dxa (по умолчанию поровну на полезную
ширину 9355 dxa); `header` по умолчанию `true`. `\n` в ячейке создаёт
новый абзац, а строки таблицы не разрываются между страницами.

Относительные пути внутри content.json — от папки самого content.json.
Титульный лист, колонтитул с номером страницы (скрыт на титуле), поля A4 и шапку второй страницы («Лабораторная работа №N» и «по теме …») скрипт делает сам по `--num`, `--theme` и данным из `_context.json`. Поэтому при обычной сборке не добавляй эти два заголовка первыми элементами `content.json`: начинай с содержательного раздела («Цель работы», «Задание», «Ход работы»). Сборщик диагностирует точный дубль до создания DOCX. Полное описание формата — в докстринге `_tools/make_docx.py`.

Для ручной структурной проверки используй bundled-инспектор с ASCII-safe
путём: `py C:\tools\lab-skill\scripts\inspect_docx.py C:\work\report.docx --summary`.
Если bundled-инспектор недоступен, используй проектный `_tools/inspect_docx.py`.
Для проверки итоговой пары документов предпочитай runner-действие
`inspect-documents`.
Если выбранный инспектор не поддерживает `--summary`, запусти его без флага;
это не является ошибкой отчёта. Полный вывод содержит проверку структуры
абзацев, таблиц, листингов и рисунков.



### ASCII-safe запуск на Windows

Не транслитерируй пользовательские данные и не меняй их кодировку. Вместо
этого держи командный интерфейс ASCII-safe: номер ЛР и флаги передавай
аргументами, а кириллические темы и пути читай из UTF-8 JSON либо собирай
внутри UTF-8-скрипта. Не передавай кириллицу через `python -c` или ненадёжные
аргументы PowerShell 5.1; логи и временные файлы называй ASCII. При сохранении
вывода Python в файл на Windows устанавливай `PYTHONUTF8=1`.

Для стандартной сборки используй bundled runner: он читает тему и пути из
`_lab_state.json`, поэтому тема не передаётся через shell. Runner-действия
`build-text`, `build-pdf`, `inspect-documents` и `prepare-report` также не
передают через shell пути, тему или иные пользовательские значения из состояния.
Это намеренно исключает передачу кириллических путей и тем в оболочку.

Если корень содержит кириллицу, запускай команды **из корня проекта** и
передавай только ASCII `.` и ASCII-путь к каталогу скилла (здесь
`C:\tools\lab-skill` — пример такого пути):

```text
py C:\tools\lab-skill\scripts\lab_runner.py --root . --lab 1 --action validate-state
py C:\tools\lab-skill\scripts\lab_runner.py --root . --lab 1 --action build-report
py C:\tools\lab-skill\scripts\lab_runner.py --root . --lab 1 --action build-text
py C:\tools\lab-skill\scripts\lab_runner.py --root . --lab 1 --action build-pdf
py C:\tools\lab-skill\scripts\lab_runner.py --root . --lab 1 --action inspect-documents
py C:\tools\lab-skill\scripts\lab_runner.py --root . --lab 1 --action quality-gate
py C:\tools\lab-skill\scripts\lab_runner.py --root . --lab 1 --action verify-quality
py C:\tools\lab-skill\scripts\lab_runner.py --root . --lab 1 --action prepare-report
py C:\tools\lab-skill\scripts\lab_runner.py --root . --lab 1 --action capture-cli
py C:\tools\lab-skill\scripts\lab_runner.py --root . --lab 1 --action check-screenshot
```

`--root` по умолчанию равен `.`; абсолютный путь передавай лишь если он уже
ASCII-safe. В выбранной записи `labs.N` обязательна непустая `theme`; `content`,
`report` и `context` необязательны и по умолчанию используют стандартные пути.
`--lab N` выбирает запись состояния, а не обязательно официальный номер: для
титульника runner берёт `report_number`, если оно задано. `directory`
переопределяет рабочий каталог `ЛРN`; указанная `methodical_guide` проверяется
до сборки.

`validate-state` проверяет метаданные без требования готового отчёта: типы
полей, относительность путей, дубликаты артефактов, переносимость `commands` и
ссылки `bundled:`. `capture-cli` требует `labs.N.commands.cli_evidence` и ровно один `img` сразу после раздела «Результат выполнения»; он сохраняет новый PNG в этот путь. `check-screenshot` выполняет безопасную проверку такого PNG без открытия предпросмотра. `build-text` собирает `text.docx`: по умолчанию читает
стандартный `content_text.json`, а поля записи `text_content` и `text` могут
переопределить соответственно источник содержимого и путь итогового документа.
`build-pdf` создаёт PDF из DOCX сначала через Word COM, затем через LibreOffice
как fallback. Если оба способа недоступны либо конвертация не удалась, runner
завершается блокирующей ошибкой; нельзя считать PDF или quality gate успешными.

`inspect-documents` структурно проверяет оба DOCX-документа — отчёт и
`text.docx` — и извлекает текст PDF для содержательной проверки (пустые
страницы, пропавшие или нарушившие порядок разделы). `prepare-report` выполняет
полный цикл: собирает отчёт и конспект,
создаёт PDF, запускает инспекцию документов и quality gate. Используй его после
готовности исходных материалов; при любой блокирующей ошибке он останавливается
и не объявляет работу готовой.

`quality-gate` дополнительно проверяет структуру DOCX-отчёта и `text.docx`,
сигнатуру PDF, а для исполнимых работ — PNG-доказательство (сигнатура, IHDR и минимум 640×360), и только при успехе атомарно записывает `ЛРN/quality_gate.json` с
SHA-256-манифестом входных и итоговых файлов. Этот файл содержит версию схемы,
UTC-время, перечень проверок, относительные пути финальных документов и хеши;
он не заменяет проверку текста PDF. После любых правок отчётных материалов
запускай `verify-quality`: команда подтвердит актуальность `quality_gate.json`
либо потребует повторить `quality-gate`. Runner останавливается с понятной
ошибкой, если состояние или артефакты неполны.

## Скриншоты для отчёта (cdp.js + shot.ps1)

Для CLI-работ используй `run_cli_shot.ps1` через runner-действие `capture-cli`: оно запускает указанную в `labs.N.commands.cli_evidence` команду в отдельной UTF-8 консоли, назначает уникальный заголовок и вызывает `shot.ps1` строго по нему. Это не позволяет случайно снять Zed, старое окно терминала или весь рабочий стол. После съёмки `check-screenshot` проверяет только сигнатуру PNG и его размер; он **не открывает изображение**, не создаёт окон и не меняет фокус. Пример записи состояния:

```json
"commands": {
  "cli_evidence": "py app.py"
}
```

Не используй `-Active` для отчётного CLI-доказательства, кроме исключительного случая, когда окно уже вручную проверено: `-Active` легко захватывает редактор. Для ручного нативного снимка используй `shot.ps1 -Title` с уникальной подстрокой заголовка.

Для браузерных лабораторных основной инструмент — CDP-харнес
`<папка скилла>\scripts\cdp.js` (Node ≥ 22, без зависимостей; Edge запускает
сам с `--remote-debugging-port`, профиль в `%TEMP%\edge-cdp-profile`).
`launch` только стартует браузер, `run` подключается и выполняет действия
в порядке аргументов — почти всегда нужна пара команд. По умолчанию профиль
находится в `%TEMP%\edge-cdp-profile`; для изолированного прогона передай один
и тот же каталог в `launch` и `reset`: `--profile-dir <ASCII-путь>`. `reset`
пытается удалить профиль до трёх раз с короткими паузами, что устраняет
временные блокировки Edge на Windows:

1. **Статика** (страница как есть) — headless, быстро и детерминированно:
   `node cdp.js launch --headless` →
   `node cdp.js run --file lab\ex1.html --wait 300 --shot lab\screenshots\ex1.png`

      `--file` предпочтительнее ручного `file:///` URL: харнес сам корректно
      экранирует пробелы и кириллицу в пути.
2. **Интерактив** (JS-эффект, состояние после действий) — та же очередь:
   `... run --url ... --eval "document.body.style.backgroundColor='red'" --shot out.png`
   (результат `--eval` печатается — используй и как функциональную проверку).
   Анимации: `--nowait-eval "..." --wait 1500 --shot out.png`.
3. **Диалоги** (alert/confirm/prompt) — **только обычное окно, не headless**:
   диалоги живут лишь в реальном окне, и Edge закрывает их, как только
   отключается последний DevTools-клиент. Поэтому снимок — `--os-shot`
   (вызов `shot.ps1` поверх окна Edge) **при живом CDP-соединении**, а обработка —
   `--dialog-action accept[:текст]|dismiss` прямо в очереди:
   `... run --url ... --nowait-eval "prompt('password?')" --os-shot s1.png --dialog-action accept:answer --shot s2.png`
4. **Popup / новое окно** — открывай только доверенным щелчком
   `--click "селектор"` (Input.dispatchMouseEvent даёт user activation, и
   popup-блокироватор молчит; программный `.click()` — нет), затем
   `--match <подстрока заголовка>` + `--shot`.

Грабли из практики:

- **Кириллица в командах искажается** при передаче через CDP: в `--eval`,
  текстах диалогов и `--dialog-action:...` держи ASCII, кириллицу собирай
  в JS из юникода — `'\u0437\u0434\u0440\u0430\u0432\u0441\u0442\u0432\u0443\u0439'`.
- CSS-позиции обязаны иметь единицы: `style.top = '100px'`, а не `'100'`
  (без `px` в standards mode игнорируется).
- Прогон завис / поплыли снимки: выполни `node cdp.js reset` — команда штатно
  закрывает доступный CDP-браузер и до трёх раз пытается удалить
  `%TEMP%\edge-cdp-profile`. Для изолированного профиля используй тот же
  `--profile-dir`, что и при `launch`. Если профиль всё ещё занят сторонним
  процессом после повторов, команда завершится понятной ошибкой, не удаляя
  другие профили.
- Всё в `ЛРN/screenshots/`, имена — по смыслу страницы/состояния
  (`index.png`, `dialog_prompt.png`, `after_click.png`).

`shot.ps1` сам по себе полезен и для ОС-уровня: `-Process msedge`,
`-Title "подстрока"`, `-X/-Y/-W/-H` для региона, `-Active`.



Разделяй доказательства по типу: CDP — для веб-страницы, DOM и браузерного
интерактива; `shot.ps1` либо глобальный скилл `screenshot` — для нативных
окон (Postman, терминал, IDE, отчёты); Selenium/Appium fixture — для снимка
падения UI-теста. Для CLI-валидатора включай в отчёт настоящий снимок окна
терминала с фактическим выводом, а не HTML-страницу, воспроизводящую лог.
Перед ОС-снимком по возможности разверни окно, а после снимка закрой его или
верни пользователю фокус; явно сообщи о возврате управления.

## PDF (docx2pdf.ps1)

Предпочтительный способ — runner-действие `build-pdf`: оно сначала использует
MS Word через COM, затем LibreOffice как fallback, и не передаёт через shell
кириллические пути или тему. При отсутствии либо сбое обоих способов runner
должен завершиться блокирующей ошибкой; не переходи к успешному quality gate.

Для ручного запуска используй только уже ASCII-safe пути, например:

```text
powershell -ExecutionPolicy Bypass -File C:\tools\lab-skill\scripts\docx2pdf.ps1 -Docx C:\work\report.docx -Pdf C:\work\report.pdf
```

Если ручная конвертация также не имеет ни Word, ни LibreOffice, сообщи точную
блокирующую причину и запроси доступный способ конвертации.



## Проверка отчёта — обязательный quality gate

Не объявляй лабораторную готовой только по факту создания файлов. После сборки
выполни и зафиксируй в `_lab_state.json`:

1. предпочтительно `lab_runner.py --action inspect-documents`: он структурно
   проверяет оба DOCX-документа и извлекает текст PDF для содержательной
   проверки. При ручной проверке используй `inspect_docx.py` для структуры,
   `docx_text.py` для текста DOCX и `pdf_text.py` для текста PDF;
2. DOCX → PDF через `build-pdf`: Word COM, затем LibreOffice. Отсутствие или
   сбой обоих конвертеров — блокирующая ошибка, не успешная проверка;
3. сверку с методичкой: все обязательные разделы, ссылки на файлы, листинги,
   таблицы и изображения существуют. `lab_runner.py --action verify-report`
   дополнительно проверяет каждый `codefile` и `img` из `content.json`;
4. после сборки всех документов выполни `lab_runner.py --action quality-gate`:
   он подтверждает ссылки, артефакты, структуру DOCX-отчёта и `text.docx`, а
   также сигнатуру PDF;
5. проверь `text.docx`: в нём есть объяснение работы, порядок демонстрации с
   путями и вопросы с подготовленными ответами. Когда нужны все этапы,
   `prepare-report` заменяет разрозненные сборку, инспекцию и quality gate.

После каждого изменения `_lab_state.json` сначала проверь синтаксис командой,
работающей одинаково в PowerShell, cmd.exe и POSIX-совместимых оболочках:

```sh
py -c "import json, pathlib; json.loads(pathlib.Path('_lab_state.json').read_text(encoding='utf-8'))"
```

Затем запусти `py <папка скилла>\scripts\lab_runner.py --root . --lab N
--action validate-state`. Для старых ЛР с историческими абсолютными путями
сначала перенеси команды в относительные либо `bundled:` ссылки; обычные старые
проверки остаются обратно совместимыми до явного запуска этого действия.

Не используй перенаправление `> NUL`: вне `cmd.exe` оно может создать лишний
файл `NUL` в корне проекта.

Если пересборка DOCX блокируется открытым Word или просмотрщиком, runner сохраняет новую временную копию рядом с отчётом и указывает её путь. Не удаляй её: закрой документ, затем повтори сборку и только после успешной атомарной замены удали временную копию. Не завершай процесс Word автоматически без прямого согласия пользователя. Если проверка блокируется внешней причиной (например, нет Word и LibreOffice), сообщи точную причину и не выдавай её за успешный quality gate.

## text.docx — конспект для защиты

Назначение: всё для подготовки к защите и самой защиты. Имя `text.docx`
выбрано неброским специально — не менять. Собирается тем же сборщиком, но
без титульного листа и шапки — это личный конспект, не отчёт:

При путях или теме с не-ASCII символами используй runner-действие
`build-text`. Ручной запуск допустим только с ASCII-safe аргументами:

```text
py _tools\make_docx.py --out lab\text.docx --num 1 --theme "Sample theme" --content lab\content_text.json --no-title
```

Без титульного листа `--context` не нужен. В `content_text.json`
(отдельный файл, лежит рядом с content.json):

- кратко: что сделано и как это устроено;
- как демонстрировать принимающему: какие файлы открыть, в каком порядке,
  что показать на каждом шаге (с путями);
- вероятные вопросы по теме лабораторной работы + заготовленные ответы.

## Восстановление окружения

Если проект открыт без инструментов (другая машина, новая копия, что-то
потерялось):

1. Прочитай докстринги того, что уже есть в `_tools/` проекта, и используй
   проектные харнесы первыми — на другой машине они могли быть доработаны
   и не совпадать с bundled-версией.
2. `_tools/make_docx.py` отсутствует → восстанови из скилла:
   `Copy-Item <папка скилла>\scripts\make_docx.py _tools\`
   (если титульник вуза был адаптирован — проверь, что адаптация сохранилась).
3. `make_docx.py` на месте, но нет флагов `--context` / `--no-title` —
   локальная версия устарела: сверь с bundled из скилла и допиши недостающие.
4. Остальные инструменты (`cdp.js`, `shot.ps1`, `pdf_text.py`, `docx_text.py`,
   `inspect_docx.py`, `lab_runner.py`, `docx2pdf.ps1`) не копируются — бери из
   `<папка скилла>\scripts\` (одна копия = нет расхождений).
5. `_context.json` отсутствует → Шаг 0, данные не выдумывать.
6. Для PDF — Word (COM) или LibreOffice, см. раздел «PDF».
7. Правишь `_tools/make_docx.py`: общие улучшения (багфиксы, формат
   content.json — всё, что не привязано к вузу) скопируй и в
   `<папка скилла>\scripts\make_docx.py`, чтобы копии не разошлись.
   Вуз-специфичную адаптацию титульника оставляй только в `_tools/` —
   в скилл её не копируй.
