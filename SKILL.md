# Лабораторные работы по ИТ-дисциплинам — универсальный workflow

Скилл для выполнения лабораторных работ по программированию и ИТ-дисциплинам
в любом вузе, для любого студента и любого принимающего. Не привязан ни к
вузу, ни к дисциплине, ни к исполнителю: все данные — вуз, студент,
преподаватель, вариант — берутся из опроса пользователя и `_context.json`,
никогда из предположений.

Подробные справочники вынесены в `references/`; в конце файла — таблица, что и
когда читать.

## Главные принципы

1. **Одна лабораторная работа за раз.** Никогда не начинай следующую, пока
   текущая не согласована с пользователем. Цикл: выполнил → отчитался (что
   сделано, где лежит, что проверить) → пользователь проверил → его замечания →
   правки → только потом следующая.
2. **Никаких выдуманных данных.** Вуз, ФИО, группа, преподаватель, вариант,
   тема — только из `_context.json` или из прямого ответа пользователя.
   Данных нет — спроси.
3. **Переносимость.** Все пути — относительные от корня проекта. Ничего не
   хардкодь в скриптах: каждый проект — свой контекст.
4. **Продолжение без потери контекста.** Постоянные данные титульника живут
   в `_context.json`, а ход конкретных работ — в `_lab_state.json`. При
   возобновлении сначала прочитай оба файла и не переспрашивай уже
   подтверждённое.

## Доказательство выполнения

Для каждой ЛР с исполняемым кодом (`codefile` или `code`) либо с
`commands.cli_evidence` раздел «Результат выполнения» обязан содержать PNG
фактического запуска. Текстовый `code` с ожидаемым выводом не заменяет
доказательство и может быть только пояснением рядом с изображением.

- CLI — `capture_cdp.js --cli` через runner-действие `capture-cli`: команда
  действительно выполняется, вывод попадает в кадр целиком (UTF-8/cp1251,
  ANSI-цвета, авто-высота), в кадре печатаются код возврата и пометка «вывод
  команды, отрисован автоматически». Не выдавай кадр за снимок консоли.
- Веб — CDP: `capture_cdp.js` для статики, `cdp.js` для интерактива, диалогов
  и popup.
- Нативное окно — `shot.ps1` или глобальный скилл `screenshot`.

Инструменты, команды и грабли — в `references/evidence.md`.

## Шаг 0 — сбор контекста

Прочитай `_context.json` в корне проекта (рядом с `_tools/`). На старте
проекта этого файла не существует — его создаёшь ты сам по итогам опроса.
Возможные состояния проекта:

- **голая папка** — опроси с нуля и создай всю структуру;
- **неорганизованная папка** (методички и файлы вперемешку) — опроси,
  разложи по структуре из следующего раздела;
- **организованный проект** (готовые лабораторные работы) — опроси недостающее,
  сверь структуру проекта со стандартной.

Если в проекте есть иные файлы с уже утверждёнными ранее данными (план
работ, README, `_context.json` смежного проекта) — используй их как источник:
не переспрашивай того, что там уже подтверждено, спрашивай только то,
чего не хватает.

Если `_context.json` уже есть (создан при прошлых работах) — не опрашивай
с нуля: покажи пользователю текущие данные и попроси подтвердить, что они
актуальны. Если файла нет или какие-то поля пусты — спроси у пользователя
ВСЁ недостающее одним списком:

- вуз/институт/кафедра и **образец титульного листа** (файл, скан или текст);
- ФИО и группа студента;
- ФИО, должность и учёное звание принимающего преподавателя;
- город и учебный год, дисциплина;
- номер варианта выполнения;
- тема лабораторной работы и методичка (файл или ссылка);
- особые требования к отчёту и порядку сдачи;
- используется ли git; если репозитория нет — нужно ли инициализировать.

Шаблон `_context.json`:

```json
{
  "university": ["строки шапки титульника", "по порядку"],
  "discipline": "",
  "student": "", "group": "",
  "teacher": "", "teacher_title": "",
  "city": "", "year": "",
  "variant": "",
  "git": true
}
```

`university` — список строк верхней части титульного листа в порядке
следования; остальные титульные поля идут как есть; `variant` нужен для
выбора задания из методички; `git` — использовать ли git в этом проекте.
Заполнив — сохрани файл и продолжай.

## Шаг 0.5 — единица сдачи

Число заданий ≠ число файлов. Определи, что сдаётся: один артефакт, который
задания дополняют, или отдельный на каждое задание. Признаки накопительной
работы: единственное число («откройте свою страницу», «дополните программу»),
ссылка задания N на результат N−1, задания описывают слои одной сущности.
Признаки независимых заданий: «для каждого задания — отдельный файл» либо
задания не ссылаются друг на друга. По умолчанию — **одна накопительная
единица**; при противоречии задай пользователю один вопрос, не угадывай.

Решение запиши в `_lab_state.json`:
`"deliverable": {"kind": "single"|"per_task", "paths": [...]}`.
Перед quality gate проверь: файлы, совпадающие на 80%, — это одна работа,
сведи её к одному.

## Состояние работ — `_lab_state.json`

`_context.json` содержит постоянные данные студента и титульного листа. Для
переноса работы между сессиями и компьютерами веди рядом с ним
`_lab_state.json`: он хранит изменяемое состояние лабораторных и
подтверждённые проектные решения, но не дублирует персональные данные или
текст заданий из методичек.

Методичка, указанная в `methodical_guide`, — первичный источник официального
номера, темы, задания и требований. Имя каталога — только рабочий путь. Если
данные методички противоречат `report_number` или `theme` в состоянии,
покажи противоречие пользователю и запроси уточнение, а не выбирай молча.

```json
{
  "version": 2,
  "commit_on_completion": false,
  "project_notes": ["Подтверждённое решение проекта, которого нет в методичке"],
  "labs": {
    "1": {
      "status": "in_progress",
      "directory": "ЛР1",
      "methodical_guide": "ЛР1/методичка.pdf",
      "report_number": 9,
      "theme": "Тема лабораторной работы",
      "variant": "9",
      "shared_resources": ["_libs/библиотека.js"],
      "notes": ["Подтверждённое решение именно этой ЛР"],
      "next_step": "Собрать и проверить отчёт",
      "commands": {"build_report": "py _tools/make_docx.py ..."},
      "command_templates": {"functional_check": "node cdp.js run --url file:///..."},
      "tooling": {"report_inspector": "bundled:inspect_docx"},
      "verification": {
        "status": "passed",
        "checked_at": "2026-10-01T12:34:56Z",
        "checks": ["content_references", "artifacts", "report_structure"],
        "warnings": []
      },
      "artifacts": ["ЛР1/Отчет_ЛР1.docx"]
    }
  }
}
```

- `directory` — необязательный относительный рабочий каталог; по умолчанию
  `ЛР<ключ labs>`. `report_number` — официальный номер для титульника;
  по умолчанию ключ записи. Абсолютные пути запрещены.
- `shared_resources` — относительные ссылки на общие ресурсы, которые не надо
  копировать в каждую ЛР. `artifacts` перечисляет готовые файлы и каталоги
  результатов (например, `screenshots/`).
- `commands` — только фактически выполненные и воспроизводимые команды без
  абсолютных путей к профилю пользователя или глобальному скиллу.
  `command_templates` — схемы и команды с подстановками.
- `tooling` — логические ссылки на bundled-скрипты (`bundled:inspect_docx`,
  `bundled:pdf_text`, `bundled:docx2pdf`, `bundled:docx_text`, `bundled:cdp`,
  `bundled:capture_cdp`, `bundled:shot`, `bundled:lab_runner`).
- `verification` — сводка последней проверки; она не заменяет повторный gate.
- Допустимые `status`: `not_started`, `in_progress`, `ready_for_review`,
  `completed`. Создавай записи только для известных лабораторных.

Жизненный цикл: перед практической частью — `in_progress` и ближайший шаг в
`next_step`; после каждого изменения состояния — `validate-state`; только
после успешного gate (он создаёт `ЛРN/quality_gate.json`) — `ready_for_review`;
после явного подтверждения пользователя — `completed`.

`commit_on_completion` по умолчанию `false`: коммит только по прямому запросу
пользователя либо при явно включённом флаге.

## Выполнение лабораторной работы — workflow

1. Уточни номер лабораторной работы. Задание ищи в методичке:
   PDF читай сначала read-инструментом, а если он PDF не берёт — извлеки
   текст действием `read-guide` (см. `references/tools.md`). Если методичка
   относится только к этой ЛР и лежит в корне или в неорганизованной папке —
   **перемести, а не копируй** её в `ЛРN/` до начала практической части и
   укажи новый относительный путь в `_lab_state.json`. Исключение — явно
   общая методичка для нескольких ЛР: оставь один экземпляр в общем месте и
   зафиксируй его как общий ресурс.
2. Выполни всю работу в папке `ЛРN/`.
3. Сними доказательства в `ЛРN/screenshots/`, добавь их в `artifacts` и
   вставь элементом `img` после заголовка «Результат выполнения». Для CLI
   предпочитай `capture-cli`, затем `check-screenshot`. Подробности —
   `references/evidence.md`.
4. Собери отчёт (см. `references/report-format.md`) → `ЛРN/Отчет_ЛРN.docx`.
5. Собери `ЛРN/text.docx` действием `build-text`.
6. Конвертируй отчёт в PDF действием `build-pdf` → `ЛРN/Отчет_ЛРN.pdf`.
7. Выполни `inspect-documents`, затем `quality-gate`; сохрани команды и
   подтверждённые файлы в `_lab_state.json` и поставь `ready_for_review`.
   `prepare-report` выполняет полный цикл одним действием.
8. Отчитайся пользователю: что сделано, где лежит, что проверить. Жди
   проверки, вноси правки до согласования; после согласования поставь
   `completed`.
9. Если в проекте используется git — предложи коммит в стиле существующих в
   репозитории (посмотри `git log`), например `LR3: краткая суть работы`.
   Выполняй его только по прямому запросу либо при
   `commit_on_completion: true`.

Команды для типового цикла:

```text
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action build-report
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action build-text
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action build-pdf
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action quality-gate
```

## Проверка отчёта — обязательный quality gate

Не объявляй лабораторную готовой только по факту создания файлов. Гейт
проверяет наличие и содержание:

- ссылки `codefile` и `img` из `content.json` существуют;
- артефакты из `artifacts` на месте;
- DOCX-отчёт, PDF и `text.docx` — валидные контейнеры;
- в `content.json` не меньше трёх разделов и двух абзацев;
- все заголовки присутствуют в DOCX в том же порядке;
- число рисунков и таблиц в DOCX совпадает с `content.json`;
- `text.docx` не короче 300 символов и не содержит заглушек;
- PDF содержит не меньше двух страниц (через PyMuPDF, если установлен);
- PNG-доказательство не одноцветное и не меньше 640×360.

При успехе gate атомарно пишет `ЛРN/quality_gate.json` со схемой, временем,
списком проверок, предупреждениями и SHA-256-манифестом. После любых правок
запускай `verify-quality`: он подтвердит актуальность записи либо потребует
повторить `quality-gate`. Если проверка заблокирована внешней причиной
(например, нет Word и LibreOffice), сообщи точную причину и не выдавай её за
успешный gate.

## Структура проекта

```
ЛРN/                  — лабораторные работы по одной в папке (ЛР1, ЛР2, ..., ЛРN)
  код работы          — исходники, страницы, данные лабораторной
  screenshots/        — PNG-скриншоты для отчёта
  img/, downloads/    — по необходимости работы
  content.json        — содержимое отчёта
  content_text.json   — содержимое text.docx
  Отчет_ЛРN.docx      — отчёт
  Отчет_ЛРN.pdf       — тот же отчёт в PDF
  text.docx           — конспект для защиты (имя неброское — так задумано)
  quality_gate.json   — подтверждение успешной проверки
_libs/                — необязательно: локальные общие зависимости нескольких ЛР
_tools/make_docx.py   — сборщик .docx
_context.json         — постоянные данные контекста (титульник, вариант, git)
_lab_state.json       — ход лабораторных, команды и готовые артефакты
```

Имена `text.docx` и `Отчет_ЛРN.*` — фиксированные соглашения, не переименовывать
и не «улучшать». Если попались старые/иные имена отчётов — приведи к стандарту
при очередной работе с этой лабораторной.

## Обновление скилла

Если скилл установлен в нескольких местах (`~/.agents/skills/lab-works`,
`~/.gemini/config/skills/lab-works`), сверь копии перед работой:

```text
py <папка скилла>\scripts\install_skill.py --check
```

Расхождение означает, что агент может исполнять старую версию; обнови копии
командой `install_skill.py` (она делает бэкап и проверяет SHA-256).
