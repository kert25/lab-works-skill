# Инструменты и runner: команды, переносимость, обновление

Справочник по bundled-скриптам и `lab_runner.py`. Читай перед запуском
команд в новом окружении, при восстановлении проекта и при обновлении скилла.

## Набор инструментов

| Файл | Назначение | Где живёт |
|---|---|---|
| `make_docx.py` | сборщик .docx (отчёт, конспект) | копируется в `_tools/` проекта |
| `docx2pdf.ps1` | docx → pdf (Word COM) | из папки скилла |
| `cdp.js` | CDP-управление Edge: снимки страниц, JS, диалоги, popup; `reset` очищает зависший профиль | из папки скилла |
| `capture_cdp.js` | одношаговый снимок HTML-страницы или CLI-вывода через Edge Headless (Node ≥ 22) | из папки скилла |
| `shot.ps1` | снимок окна/региона ОС | рядом с `cdp.js` |
| `pdf_text.py` | извлечение текста из PDF (PyMuPDF) | из папки скилла |
| `docx_text.py` | извлечение текста из DOCX | из папки скилла |
| `inspect_docx.py` | структурная проверка абзацев, таблиц, листингов и рисунков DOCX | из папки скилла |
| `lab_runner.py` | ASCII-safe сборка, конвертация и проверка по `_lab_state.json` | из папки скилла |
| `install_skill.py` | установка/обновление скилла в каталоги агента | только в репозитории |

Дублируется в `_tools/` только `make_docx.py` — он единственный, кто
адаптируется под проект/вуз. Остальные запускай напрямую из папки скилла,
копии не нужны. Если у проекта уже свои харнесы в `_tools/` — сначала прочитай
их докстринги и используй их.

Если в проекте нет `_tools/make_docx.py`:

1. `Copy-Item <папка скилла>\scripts\make_docx.py _tools\`
2. Сверь титульный лист с образцом вуза (см. `references/report-format.md`).
3. Создай `_context.json` (Шаг 0) и проверь генерацию на пробном отчёте.

Если в проекте уже есть свой сборщик отчётов или шаблон — сравни его с
bundled-версией (возможности, формат содержимого, кодировка, рисунки,
листинги). Если реализация хуже — предложи пользователю доработать или
заменить; молча не заменяй.

## runner: действия

```text
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action validate-state
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action build-report
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action build-text
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action build-pdf
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action inspect-documents
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action quality-gate
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action verify-quality
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action prepare-report
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action capture-cli
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action check-screenshot
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action read-guide --out guide.txt
py <папка скилла>\scripts\lab_runner.py --root . --lab 1 --action init-text
```

`--root` по умолчанию равен `.`; абсолютный путь передавай лишь если он уже
ASCII-safe. В выбранной записи `labs.N` обязательна непустая `theme`;
`content`, `report` и `context` необязательны и по умолчанию используют
стандартные пути. `--lab N` выбирает запись состояния, а не обязательно
официальный номер: для титульника runner берёт `report_number`, если оно
задано. `directory` переопределяет рабочий каталог `ЛРN`; указанная
`methodical_guide` проверяется до сборки.

- `validate-state` — типы полей, относительность путей, дубликаты артефактов,
  переносимость `commands`, ссылки `bundled:`. Запускай после каждого
  изменения `_lab_state.json`.
- `read-guide` — текст методички (`.docx` или `.pdf`) в консоль или файл.
  Для PDF используется первый доступный бэкенд (PyMuPDF, pypdf, `pdftotext`);
  если нет ни одного — понятная ошибка. Таблицы DOCX извлекаются как Markdown,
  поэтому таблица вариантов не смешивается с соседними абзацами.
- `init-text` — стартовый `content_text.json` с вопросами из методички.
  Распознаются разные заголовки: «контрольные вопросы», «вопросы к зачёту»,
  «вопросы для коллоквиума», «тестовые вопросы» и близкие; раздел
  останавливается на «приложении», списке литературы и требованиях к оформлению.
  Ответы в нём — заглушки, их нужно заменить.
- `build-report` / `build-text` — сборка DOCX из `content.json` и
  `content_text.json`; тема и пути читаются из состояния, а не из shell.
- `build-pdf` — DOCX → PDF: сначала Word COM, затем LibreOffice. Если оба
  способа недоступны, runner завершается блокирующей ошибкой; успешный gate
  без PDF невозможен.
- `inspect-documents` — структурная проверка обоих DOCX и извлечение текста
  PDF для содержательной проверки.
- `prepare-report` — полный цикл: отчёт, конспект, PDF, инспекция, gate.
  Останавливается на первой блокирующей ошибке.
- `quality-gate` — см. раздел проверки в `SKILL.md`.
- `verify-quality` — подтверждает, что `quality_gate.json` не устарел после
  правок; при расхождении требует повторить gate.
- `capture-cli` / `check-screenshot` — см. `references/evidence.md`.

## ASCII-safe запуск на Windows

Не транслитерируй пользовательские данные и не меняй их кодировку. Вместо
этого держи командный интерфейс ASCII-safe: номер ЛР и флаги передавай
аргументами, а кириллические темы и пути читай из UTF-8 JSON либо собирай
внутри UTF-8-скрипта. Не передавай кириллицу через `python -c` или ненадёжные
аргументы PowerShell 5.1; логи и временные файлы называй ASCII. При сохранении
вывода Python в файл на Windows устанавливай `PYTHONUTF8=1`.

Если корень содержит кириллицу, запускай команды **из корня проекта** и
передавай только ASCII `.` и ASCII-путь к каталогу скилла (пример такого
пути — `C:\tools\lab-skill`, но подставь фактический).

## PDF

Предпочтительный способ — `build-pdf`: Word COM, затем LibreOffice. При
отсутствии обоих — блокирующая ошибка, не успешный gate.

Для чтения PDF (`pdf_text.py`, `read-guide`) используется каскад:
PyMuPDF → pypdf → `pdftotext` из Poppler. Достаточно любого одного.

Ручной запуск только с ASCII-safe путями:

```text
powershell -ExecutionPolicy Bypass -File <папка скилла>\scripts\docx2pdf.ps1 -Docx C:\work\report.docx -Pdf C:\work\report.pdf
```

Если Word уже запущен пользователем, скрипт не закрывает его экземпляр: COM
может подключиться к существующему процессу, и `Quit()` закрыл бы чужие
документы.

## Восстановление окружения

Папка скилла — каталог, в котором лежит `SKILL.md`. Если проект открыт без
инструментов (другая машина, новая копия):

1. Прочитай докстринги того, что уже есть в `_tools/`, и используй проектные
   харнесы первыми — они могли быть доработаны.
2. `_tools/make_docx.py` отсутствует → скопируй из `scripts/` скилла
   (проверь, что адаптация титульника сохранилась).
3. `make_docx.py` на месте, но нет `--context`/`--no-title` — версия устарела,
   сверь с bundled.
4. Остальные инструменты не копируются — бери из папки скилла.
5. `_context.json` отсутствует → Шаг 0, данные не выдумывать.
6. Для PDF — Word (COM) или LibreOffice.
7. Правишь `_tools/make_docx.py`: общие улучшения копируй и в
   `scripts/make_docx.py`; вуз-специфичный титульник оставляй только в проекте.

## Обновление установленной копии

Если скилл установлен в каталоги агента (`~/.agents/skills/lab-works`,
`~/.gemini/config/skills/lab-works`), обновляй их из репозитория одной командой:

```text
py <папка скилла>\scripts\install_skill.py --check     # только сравнить
py <папка скилла>\scripts\install_skill.py             # обновить с бэкапом
```

Скрипт пропускает dev-каталоги, проверяет копию по SHA-256 и откатывается при
ошибке. Предыдущая версия сохраняется рядом как `lab-works.backup-<время>`.
