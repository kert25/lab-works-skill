# Как участвовать в `lab-works`

Спасибо, что дошли до этого файла. Проект небольшой, поэтому правила короткие,
но выполняются буквально: часть из них проверяют тесты и CI, остальное — ревью.

## Подходит ли вклад

Приветствуется:

- **eval-сценарии из реальных методичек** — самое ценное: они показывают, где
  навык ломается на настоящих заданиях;
- исправления Windows-специфики: COM/Word, кодировки консоли, CDP, блокировки
  файлов антивирусом;
- уточнения в `references/`, если они исправляют конкретный наблюдавшийся сбой;
- новые методички в `evals/corpus/` — при наличии права на их распространение;
- документация, шаблоны задач, исправления опечаток.

Не будет принято:

- изменения `SKILL.md` без воспроизводимого прогона, на котором видно улучшение;
- новые зависимости в `scripts/` (там только стандартная библиотека), «удобные»
  обёртки над `pip install`;
- переименование `Отчет_ЛРN.docx`, `text.docx`, `screenshots/` или смена
  структуры проекта: это фиксированные соглашения скилла;
- ослабление доказательств и quality gate «ради скорости»;
- реальные персональные данные, чужие методички и токены в коде, тестах, задачах
  и фикстурах.

## Прежде чем открыть PR

| Ситуация | Куда идти |
|---|---|
| Ошибка в работе скилла | задача по шаблону «Баг-репорт» |
| Уязвимость или утечка данных | **приватно**, по [`SECURITY.md`](SECURITY.md); не открывайте публичный issue |
| Крупное изменение (новый этап workflow, новый инструмент) | сначала задача с описанием подхода |
| Нарушение правил общения | [`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md) |

## Окружение

- Windows 10/11, PowerShell.
- Python 3.10+. Используйте `py`: в некоторых окружениях `python` — заглушка
  Microsoft Store, которая завершается с кодом `9009`.
- Node.js ≥ 22 — для CDP-инструментов.
- Microsoft Edge или Google Chrome; Microsoft Word или LibreOffice для PDF.
- Для проверок, которым нужен PDF-бэкенд: `py -m pip install --user pymupdf`.

Строки в репозитории хранятся с LF (`.gitattributes`), поэтому отключите
автоконвертацию, иначе получите ложные диффы:

```text
git config core.autocrlf false
```

## Запуск проверок

Полный набор — три команды. Запускайте их перед push:

```text
py -m unittest discover -s scripts/tests -p "test_*.py"
node --test scripts/tests/test_cdp.js
node --test scripts/tests/test_capture_cdp.js
```

Структура скилла и каталог eval проверяются отдельно — CI этого **не** делает:

```text
py .skill-eval/pipeline.py check
```

`py .skill-eval/pipeline.py test` объединяет всё перечисленное. Для PDF-тестов
нужен хотя бы один бэкенд из PyMuPDF / pypdf / `pdftotext`.

## Изменение поведения навыка

`SKILL.md` — инструкция, а не эссе: любая правка меняет то, что делает агент,
и должна опираться на факт, а не на мнение.

1. Опишите сбой воспроизводимым сценарием в `evals/` (см.
   [`.skill-eval/README.md`](.skill-eval/README.md)).
2. Прогоните пару «со скиллом / без скилла» и убедитесь, что сценарий
   различает версии. Недискриминирующие пары (оба варианта справились или оба
   провалились) не доказывают ничего — так помечен Eval 01 в
   [`EVAL_NOTES.md`](EVAL_NOTES.md).
3. Запишите результат: что подтверждено, что осталось гипотезой. Журнал ведётся
   в `EVAL_NOTES.md`, а не в PR-обсуждении.
4. Только после этого правьте `SKILL.md` или `references/`, и в PR сосчитайтесь
   на конкретный прогон.

Правила компоновки: `SKILL.md` читается всегда — держите его коротким; всё, что
можно прочитать по необходимости, живёт в `references/`. Инварианты (одна
лабораторная за раз, данные только из `_context.json`, доказательство — реальный
PNG) не выносятся в справочники и не ослабляются.

## Новая методичка в корпусе

1. Убедитесь, что материал можно хранить и публиковать в открытом репозитории.
2. Имя файла — ASCII-safe: `lr-NN-<topic>.<ext>` для лабораторной,
   `pr-NN-<topic>.<ext>` для практической.
3. Внесите запись в `evals/corpus.json`: `source_filename`, `official_number`,
   `topic`, `format`, `evaluation_value`.
4. Проверьте текстовый слой: `py scripts/pdf_text.py <pdf> 1-3` или
   `py scripts/docx_text.py <docx>`.
5. Добавьте хотя бы один сценарий в `evals/evals.json`, который эта методичка
   расширяет, и `fixtures`, если сценарий stateful.
6. Уберите персональные данные: ФИО студента, группа, номер зачётки, вариант
   конкретного человека.

## Стиль кода

- Python: только стандартная библиотека; `pathlib` вместо ручной склейки путей;
  кодировки указаны явно.
- CLI остаётся ASCII-safe: номера и флаги — аргументами, кириллица — из UTF-8
  JSON или внутри UTF-8-скрипта. Не передавайте кириллицу через `python -c` или
  аргументы PowerShell 5.1.
- Сообщения пользователю — по-русски; докстринги в новых файлах — по-английски,
  как в `scripts/lab_runner.py` и `scripts/install_skill.py`.
- Скрипты не пишут и не читают вне корня проекта, если путь не задан явно.
- Любая правка в `scripts/` сопровождается тестом в `scripts/tests/`; для Node
  используется встроенный `node:test`.
- Файлы — UTF-8, LF, перевод строки в конце. Документация — по-русски.

## Коммиты

История проекта линейная, без merge-коммитов и без Conventional Commits.
Стиль сообщения: английский, императив, с заглавной буквы, без префиксов.

```text
Add colspan and rowspan support in report tables
Drop the auto-render caption from CLI evidence frames
Harden evidence capture for headless sessions
```

Один коммит — одна причина. В теле объясняйте **почему** изменили, а не что
(что видно в диффе). Если правка следует из eval, укажите его номер.

Не коммитьте сгенерированное: `.skill-eval/workspace/`, `__pycache__`, собранные
отчёты, скриншоты прогонов, `_context.json` из личных проектов.

## Ветки и pull request

```text
git switch -c fix/cli-capture-cp1251
git push -u origin fix/cli-capture-cp1251
```

- Цель — ветка `main`. На GitVerse это merge request, на GitHub — pull request;
  шаблон описания лежит в `.github/PULL_REQUEST_TEMPLATE.md`.
- Держите ветку в актуальном состоянии через rebase, не через merge.
- CI должен быть зелёным. Он прогоняет Python- и Node-тесты на
  `windows-latest`, но **не** прогоняет `pipeline.py check` — приложите вывод
  локального запуска, если меняли структуру скилла или каталог eval.
- В описании: что сломано, как воспроизвести, какой eval или тест это
  подтверждает, что именно изменено.

Ревью — best effort: проект личный, но содержательные PR разбираются.
